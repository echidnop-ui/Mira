# Heiwa v2 Development Rules

## Как мы работаем

Пользователь не обязан проектировать реализацию.

При разработке Heiwa ассистент должен:

1. Сам определить ближайшее архитектурное изменение.
2. Сам написать готовый код.
3. Сказать, какой файл создаётся или заменяется.
4. Для небольшого файла давать полный файл.
5. Для большого файла давать точный автоматический patch.
6. Давать конкретную команду запуска.
7. По выводу терминала определять следующий шаг.
8. Не перекладывать архитектурные решения на пользователя без необходимости.

Не отвечать:

"реализуйте X"

"напишите класс Y"

"добавьте обработку Z"

если готовый код можно написать прямо сейчас.

---

## Рабочий цикл

Предпочтительно:

маленькое реальное изменение
→ запуск
→ живой результат
→ диагностика
→ следующий шаг

Не строить месяцами architecture foundation без runnable Heiwa.

## Сейчас

Текущий активный vertical slice:

DESKTOP.

Не продолжать Market только потому, что в repository существует
`worlds/market`.

Если документация или старый код противоречат текущему решению
Desktop-first, текущая документация PROJECT.md считается направлением
разработки.

---

## Experimental mode

Heiwa v2 является экспериментальной.

Можно агрессивно менять архитектуру.

Не тратить лишнюю работу на:

- backward compatibility;
- legacy checkpoint migration;
- compatibility adapters;
- rollback framework;
- формальные unit tests каждого маленького изменения.

Тест нужен, когда он отвечает на конкретный архитектурный вопрос.

---

## Не переписывать потом прототип

Мы не строим throwaway prototype.

Каждый ранний vertical slice должен использовать настоящие публичные
границы будущей архитектуры.

При этом внутреннюю реализацию органов можно менять по результатам
экспериментов.

---

## Mechanism vs cognition

Детерминированный код нормально использовать для механизмов:

- filesystem;
- OS API;
- event delivery;
- persistence;
- execution;
- permissions;
- serialization;
- screenshot capture;
- mouse/keyboard execution;
- UI parsing infrastructure.

Не хардкодить cognitive decisions.

Desktop executor может механически нажать координату.

Он не должен сам решать, куда Heiwa хочет нажать.

---

## Locality of context

Изменение одной способности не должно требовать читать весь repository.

Перед изменением определить:

TARGET MODULE

PUBLIC CONTRACT CHANGE: yes/no

FILES REQUIRED

WHY EXTERNAL FILE IS REQUIRED

Если public contract не меняется, изменение желательно удерживать внутри
одного module.

---

## MODULE.md

Перед изменением крупного модуля сначала читать его MODULE.md.

MODULE.md должен объяснять:

- PURPOSE
- INPUT
- OUTPUT
- OWNS STATE
- PUBLIC API
- DEPENDS ON
- MUST NOT
- WHAT DOES IT CAUSE?
- WHAT TRAINS IT?
- PERSISTENCE
- TELEMETRY
- FILES
- READ SCOPE FOR AI CODERS

MODULE.md — это context map, а не декоративная документация.

---

## Не сканировать repository без причины

Если меняется Desktop capture — читать Desktop module.

Если меняется Core — читать Core.

Если меняется Policy — читать Policy.

Не читать Language/Market/Game "на всякий случай".

---

## Источник истины

Когда актуальный код доступен, код является источником истины о текущей
реализации.

PROJECT.md определяет текущее архитектурное направление.

MODULE.md определяет границы конкретного органа.

Старые заметки и старые эксперименты не должны автоматически менять
текущее направление разработки.
